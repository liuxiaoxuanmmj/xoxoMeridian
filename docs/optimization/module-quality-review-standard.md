# 模块工程质量审查与持续评分标准

> 版本：1.0.0
> 生效日期：2026-09-06
> 适用范围：`PROJECT_VIEW.md` 中 QAM-01～QAM-10
> 维护目标：在既定功能范围不变的前提下，持续衡量实现本身的工程质量和长期修改成本。

## 1. 评价边界

审查回答的是：已有功能是否以边界清楚、复杂度可控、状态一致、异常可靠且便于后续修改的方式实现。

以下内容不得作为扣分理由：

- 功能数量少、页面简单、没有竞品能力或未实现当前需求之外的能力。
- 审查者偏好的命名、格式、框架或设计模式与当前实现不同，但没有可证明的质量影响。
- 为未来假想规模预建复杂架构的缺失，只要当前结构与已知变化驱动匹配。

以下内容是有效评价对象：

- 小改动是否需要跨越不相干模块，或容易形成连锁回归。
- 事实来源、状态转移、事务、异步生命周期和失败恢复是否明确。
- 依赖方向、输入/输出契约、权限边界和外部服务隔离是否稳定。
- 复杂度是否源自业务，还是源自重复、补丁叠加、隐式状态或过度抽象。
- 最高风险语义是否能通过与风险匹配的可观察行为测试得到验证。

`PROJECT_VIEW.md` 的 `In Scope`、`Out of Scope`、`Quality Risk Surface` 和 `Quality Tracking Index` 是范围依据。`Boundary Uncertainty` 只是调查入口；没有代码影响证据时不得直接登记为缺陷。

## 2. 证据纪律

每个评分和问题都必须引用当前仓库证据，并标注可信度：

| 等级 | 含义 | 可支持的结论 |
| --- | --- | --- |
| E3 | 当前快照实际执行的行为测试、真实 PostgreSQL/浏览器/Compose 验证或可复现实验 | 可以确认行为、失败或恢复语义 |
| E2 | 当前源码、schema、迁移、配置和测试实现的交叉证据，但本轮没有执行对应场景 | 可以确认结构和静态风险；行为结论需保持克制 |
| E1 | 文档、命名、注释或单点间接线索 | 只能登记为待验证观察项，不得单独形成 P0/P1 |

审查时必须遵守：

1. 同时检查主路径、失败路径、边界输入和相关测试；不得只凭文件大小或代码外观评分。
2. “没有发现问题”不等于“已证明可靠”。没有可执行证据时应降低对应维度的置信度，并登记验证缺口。
3. 不得把 mock 测试写成数据库事务、浏览器生命周期或部署拓扑已经得到真实验证。
4. 历史报告只代表当时快照。复审时重新核对链接、当前代码和验证结果，不继承已失效结论。
5. 未执行的命令必须明确标为未验证，不得用其他较低层证据替代。

## 3. 100 分评分模型

所有模块使用相同的十个维度和权重，以保持跨期、跨模块可比性。模块较小不降低评价；简单且边界合适的实现可以获得满分。

| Dimension | Max | 满分含义 |
| --- | ---: | --- |
| 架构与责任边界 | 14 | 职责、分层、依赖方向和跨 QAM 协作清楚；局部变化大体保持局部 |
| 代码结构与复杂度 | 10 | 控制流、文件和函数复杂度与业务匹配，无明显上帝对象或补丁迷宫 |
| 抽象与复用 | 8 | 共享规则有单一来源，抽象确实降低重复；没有无价值层级 |
| 数据流与状态一致性 | 12 | 事实来源、状态转移、事务、缓存和客户端同步关系明确且可恢复 |
| 接口与依赖关系 | 10 | HTTP、服务、数据和外部依赖契约稳定，具体实现耦合受控 |
| 健壮性、并发与生命周期 | 14 | 异常、重试、竞态、幂等、资源释放、重启和部分失败得到恰当处理 |
| 性能与资源使用 | 8 | 当前规模合理，并避免随数据量/连接数迅速恶化的明显路径 |
| 安全与隐私 | 10 | 认证、授权、输入、敏感数据、日志、外部调用和资源访问边界可信 |
| 可测试性与验证可信度 | 8 | 核心逻辑可隔离验证，最高风险语义有风险匹配的行为证据 |
| 可维护性、演进与技术债 | 6 | 变化驱动有清晰落点，遗留/临时代码受控，修正成本与影响面可预期 |
| **Total** | **100** | 只按当前既定功能实现质量求和 |

### 单维度评分锚点

先选择最接近的锚点，再依据证据在区间内取整数：

- 90%～100%：边界和失败语义明确，有强行为证据，没有实质性开放风险。
- 75%～89%：总体稳健，存在局部重复、耦合或验证缺口，但变化范围仍可控。
- 60%～74%：能够运行，但已有结构性债务或可靠性空白，局部变化可能跨层扩散。
- 40%～59%：多个事实来源、并发/失败语义薄弱或高风险路径难以验证，维护成本明显偏高。
- 0%～39%：关键边界失守、状态不可控或缺少基本结构；必须有直接证据，不得因“看起来简单”使用此区间。

不得用测试数量、文件数量或代码行数直接换算分数。维度不突出时，评价其是否以足够简单的方式满足当前风险，而不是标为 `N/A`；十项始终合计 100。

## 4. 分数等级与质量门禁

| Level | Score | 解释 |
| --- | ---: | --- |
| L4 | 90～100 | 成熟：边界稳定，关键失败语义有可信证据，演进成本低且可控 |
| L3 | 80～89 | 稳健：主要结构健康，少量一般债务不阻断局部演进 |
| L2 | 70～79 | 可控：核心路径可靠，但有需要计划治理的结构或验证缺口 |
| L1 | 60～69 | 脆弱：当前可运行，但改动或异常容易放大，需优先降低风险 |
| L0 | 0～59 | 失控：关键边界或一致性缺少基本保障，不能用总分掩盖 |

报告同时给出 `Score Level`、`Gate Level` 和 `Final Level`：

- `Score Level` 仅按加权总分确定。
- `Gate Level` 按以下硬条件确定；多项命中时取最低值。
- `Final Level = min(Score Level, Gate Level)`。

硬门禁：

- 存在开放 P0：`Gate Level = L0`。
- 存在开放 P1，且涉及权限绕过、不可恢复数据错误、并发重复副作用或支持启动路径失效：`Gate Level` 不高于 `L1`。
- 模块最高风险不变量没有风险匹配的行为验证：`Gate Level` 不高于 `L2`。
- `L4` 要求没有开放 P0/P1，并且关键失败、并发或生命周期路径至少有 E3 证据。

门禁不修改原始分数，便于观察连续趋势；最终等级防止平均分掩盖单点严重风险。

## 5. 问题等级与最小修正

| Priority | 使用条件 |
| --- | --- |
| P0 | 已有功能存在可被现实触发的权限边界突破、不可恢复数据损坏、重复高风险副作用、关键安全泄露或支持启动路径整体不可用 |
| P1 | 高概率造成错误状态、跨用户/跨房间影响、并发一致性破坏、持续故障或使常见小改动跨模块扩散 |
| P2 | 一般结构、可测试性、性能增长、隐私治理或技术债问题；应计划处理但当前有边界或替代路径 |

每个问题必须使用稳定 ID（如 `QAM-03-002`），并写清：

1. **问题**：具体机制，不写“建议优化架构”。
2. **证据**：仓库相对链接、行号、测试/命令和 E1～E3 等级。
3. **质量影响**：从机制到认知成本、修改成本、错误、一致性、可靠性、安全或性能后果的因果链。
4. **最小修正**：保持功能边界不变的最小结构或验证改动；不要夹带新功能。
5. **验收证据**：修正后应观察到的行为和风险匹配验证层级。
6. **影响范围**：本 QAM 及直接受影响的共享 QAM。

同一根因只登记一次；其他模块通过“关联问题”引用。纯风格差异、没有现实影响的理论风险和已有可靠控制的场景不登记为问题。

## 6. 报告固定格式

每份 `docs/optimization/qam-*-quality-review.md` 按以下顺序维护：

1. 标题与元数据：QAM、快照日期、审查 Skill、标准版本、范围来源、当前基线命令。
2. `Overall`：Score、Score Level、Gate Level / Final Level、Trend、Evidence Confidence 和不超过四句的结论。
3. `Score Breakdown`：十维表格，含 Score、Max、Finding/Evidence；末行精确合计 100。
4. `Level Gate`：逐条记录已通过和未通过门禁，以及最终等级原因。
5. `Critical Issues`：按 P0/P1/P2 展开；没有则明确写“当前无开放项”。
6. `Architecture and Data Flow`：只画或描述影响理解的边界、事实源和失败路径。
7. `Verified Strengths`：记录有证据的健康结构，防止报告只累积负面结论。
8. `Recommended Improvements`：按最小修改成本和风险收益排序；每项必须关联稳定问题 ID，不新增功能。
9. `Sustainable Review Record`：开放问题表、复审触发条件和只追加不回写的评分历史。

### 持续更新规则

- 报告正文表示“当前快照”；问题状态只允许 `open`、`resolved`、`accepted-risk`、`not-reproduced`。
- 已解决问题保留在历史表中，不删除 ID；正文可移入 resolved 小节。
- 每次复审只重算受到代码或证据变化影响的维度，但必须重新核对总分和 Gate。
- 历史表追加 `日期 / Score / Score Level / Gate / Final / Delta / 变更证据`，初审的 Delta 为 `baseline`。
- 一个提交同时改善多个模块时，每份报告独立记录本模块的直接证据；不得复制同一结论冒充多个模块已验证。
- 更新模块报告后同步 `docs/optimization/module-quality-overview.md`，但不得用总览替代详细证据。

## 7. 初审与复审工作流

1. 读取 `AGENTS.md`、`PROJECT_VIEW.md` 的对应模块、跨切关注点、共享映射和相关 Boundary Uncertainty。
2. 读取本标准和该模块既有报告；用 `git status --short` 识别未提交改动，避免把用户改动误判为历史基线。
3. 从入口、领域服务、数据模型、外部 adapter、客户端状态和测试反向追踪一条正常路径与主要失败路径。
4. 先列证据，再形成问题；对每项问题验证是否存在现有控制、是否超出功能边界、是否只是风格偏好。
5. 完成十维评分、硬门禁和问题优先级；保证算术、链接、状态和历史记录一致。
6. 只更新被授权的模块报告。审查请求本身不授权修改业务实现、数据库或部署状态。
7. 运行文档/Skill 结构检查和与本轮风险匹配的仓库门禁；原样记录未运行或失败项。

## 8. AI 生成代码专项检查

对每个模块额外核对：

- 同一规则是否在 Route、组件、Tool 或脚本中被分别生成并逐渐漂移。
- 新补丁是否绕过现有服务边界，形成第二个事实来源或平行 adapter。
- 抽象是否有两个以上真实调用方或明确隔离价值，而非只包装一次调用。
- 异常是否被局部 catch 后伪装成成功、静默吞掉或泄漏内部/敏感信息。
- 测试是否验证可观察行为，还是只锁定生成代码的字符串和内部实现。
- 修改是否在局部完成；若必须同步多个不相干文件，应追踪根因而不是继续叠补丁。

AI 生成痕迹本身不是扣分理由；只有它造成上述实际影响时才形成问题。
